## 콘텐츠 및 서비스 현황

- 검색 로직은 `src/scripts/blog.ts`로 분리하고 태그·검색 문자열은 초기화 시 한 번만 가공한다.

- 헤더 메뉴 CSS는 헤더에 한정하고 중복 CSS·언어 전환 잔여 코드를 정리했다. 검색·애니메이션 테스트를 배포 검사에 추가했다.

- Astro 정적 사이트 + GitHub Pages. Node.js 24, pnpm 11.
- 글 파일: `src/content/blog/*.md`. 현재 공개 예시 글 1개와 비공개 예시가 있다.
- 메타데이터: `title`, `description`, `date`, 선택 `time: "14:30"`(한국 시간), `tags`, `draft`.
- `draft: true`는 목록·검색·카테고리·상세 생성에서 제외한다.
- 방문자 서버: `https://chan-blog-visitors.mldlcl2022.workers.dev/`
- 서버 코드·설정: `services/visitor-counter/`. 실제 Cloudflare Worker와 D1 DB가 이미 생성·배포되어 있다.
- 엔드포인트 기본값은 `src/data/site.ts`의 `visitorCounterEndpoint`. 환경변수 `PUBLIC_VISITOR_COUNTER_URL`이 있으면 우선 사용한다.
- 사이트 전체를 한국 시간 기준 동일 브라우저 하루 한 번 집계한다. 전체는 일별 방문 수의 누적 합이다.
- `http://127.0.0.1:4330` 미리보기는 실제 통계를 GET으로 조회만 한다. 테스트로 운영 방문 수를 올리지 않는다.
- 운영 DB를 새로 만들거나 초기화하지 않는다. CMS를 도입해도 방문자 집계 서버와 콘텐츠 저장소의 역할을 구분한다.
- Cloudflare 로그인과 배포 설정은 완료되어 있다. 필요 시 CLI 로그인 상태를 확인하되 토큰을 출력하거나 저장소에 포함하지 않는다.

## 다음 작업: 웹에서 글과 카테고리 관리하기

사용자는 네이버·티스토리처럼 웹 화면에서 글 작성과 카테고리 추가·삭제를 하고 싶다는 방향을 이야기했다. **아직 CMS 제품이나 구현 방식을 확정하지 않았고 관리 화면도 구현하지 않았다.** 다음 채팅에서는 이 방향을 구체화한 후 진행한다.

### 검토할 방식

1. 기존 Astro·GitHub Pages와 Markdown 구조에 Git 기반 CMS 연결: Pages CMS 또는 Decap CMS 등이 후보.
2. 별도의 관리자 화면을 직접 제작: 화면 자유도는 높지만 인증·편집기·업로드·저장·발행 처리를 추가로 운영해야 한다.

당시 제안은 기존 CMS부터 연결하는 것이었으며 사용자의 최종 선택은 받지 않았다. 제품의 최신 지원 범위·비용·필요한 GitHub 권한을 공식 문서로 확인한 뒤 차이를 설명하고 선택한다. 외부 계정 연결이나 권한 승인은 실제 필요한 단계에서만 진행한다.

### 다음 작업의 기능 요구사항 초안

- 관리자만 로그인하여 글·이미지·카테고리를 추가/수정/삭제할 수 있다.
- 웹 화면에서 제목, 설명, 본문, 작성일·시간, 카테고리(또는 태그), 임시 저장/공개 상태를 편집한다.
- 본문은 서식 편집·이미지 삽입·코드 블록을 지원하고 기존 Markdown과 호환되어야 한다.
- 글 미리보기와 임시 저장을 제공하고, 공개 발행 시 기존 블로그 목록·검색·상세에 반영한다.
- 독립 카테고리 목록을 만들지 현재 태그 방식을 관리 화면에 노출할지 먼저 결정한다. 삭제 시 소속 글의 재분류/미분류 정책도 정한다.
- 기존 글 주소와 예시 콘텐츠의 보존/교체 여부를 확인한다. 승인 없이 기존 글을 삭제하지 않는다.
- CMS 저장 브랜치와 발행 방식을 정한다. 기존 개발은 develop → main merge지만, CMS 발행을 main 직접 반영 또는 PR/승인 방식 중 무엇으로 할지 결정해야 한다.
- 빌드 기반 발행에는 반영 시간이 있으므로 편집 화면의 저장/배포 상태를 구분한다.
- 공개 GitHub Pages 코드에 GitHub 토큰·OAuth client secret 같은 비밀 값을 넣지 않는다. GitHub App/OAuth 등 적절한 인증을 쓴다.
- PC·노트북·아이패드에서 글 작성과 이미지 업로드가 가능한지 검증한다.
- 기존 HOME·상단바·폰트·블로그 배치를 유지한다. 이번 후속 작업을 시작한다고 디자인 전면 개편까지 허용된 것은 아니다.
